## 1. What the demo shows

From the accepted description:

1. **An OpenFOAM experiment driven by RHAPSODY on DragonHPC.** A Bayesian
   optimizer tunes a turbulence parameterization while an ensemble of
   OpenFOAM runs executes asynchronously. As runs converge, their results go
   into radex, so the optimizer and other components read them from memory
   instead of files. The OpenFOAM integration is a plugin, which lowers the
   barrier for bringing existing applications into a workflow.
2. **The same workflow as a service through ORBIT.** Users do not build,
   launch and manage the RHAPSODY workflow and its resources themselves.
   ORBIT instantiates, manages and exposes it through endpoints, on demand.
   Several independent instances coexist and are used by remote clients.

The message is the general service-building pattern, with OpenFOAM as the
example: ORBIT as the service layer, RHAPSODY for workflow composition and
orchestration, ROSE for adaptive, learning-driven workflows, Dragon for
scalable distributed execution, and radex as the in-memory data plane.
Together they let users build applications without managing execution,
orchestration or data management, as a foundation for HPC and AI as a
service across the American Science Cloud.

**radex in particular:** the demo must show radex as the channel between
C++ and Python tasks. The OpenFOAM solver (C++) writes its results through
the `radexWrite` function object; Python tasks (the optimizer's result
gathering) read them from the same store, with no files in between.

**Guiding rule:** a proof of concept on the simplest OpenFOAM case that
shows all of the above. No new physics, no larger meshes, no tuning for
realism.

## 2. Workload

The OpenFOAM `pitzDaily` case with Andrew Shao's OpenFOAM plugin for
RHAPSODY,
[CrayLabs/rhapsody-plugins-openfoam](https://github.com/CrayLabs/rhapsody-plugins-openfoam),
example `examples/pitzDaily-optimize`. `pitzDaily` is the simplest case in
the plugin that has both the Bayesian optimizer and radex output; the
simpler examples (`hello-world`, `basic-openfoam`) use neither.

| Property | Value |
|---|---|
| Physics | 2D backward-facing step, steady incompressible RANS (`simpleFoam`), k-epsilon turbulence model; a standard OpenFOAM tutorial case |
| Size per case | Serial, one core; no domain decomposition |
| Tuned parameters | 4: initial `epsilon`, `Cmu`, `C1`, `C2` (`sigmaEps` derived) |
| C++ to Python via radex | `radexWrite` (C++, inside `simpleFoam`) writes `avgInlets` and the final step into radex at the end of each run; Python reads both with the radex `DragonClient` |
| Loss | `(avgInlets - target)^2` with target -1.9; converged if the solver stops before 2000 iterations |
| Optimizer | `skopt.Optimizer` with a Gaussian-process (GP) model |
| Driver | `driver-staged.py`: batches of cases run concurrently, then one `ask`/`tell` round. Simpler to show and explain than `driver-async.py` |
| Demo size | Small: about 4 cases per batch, 3-4 batches, so a run fits the video. Final values set in W8 |
| Runtime per case | About 9 s per case on one Perlmutter CPU core (5-11 s typical, one 38 s outlier per run); a full staged optimization (20 cases, 4 batches) takes 1:48 on one node ([runbook](2026-11-15-hppss-sc26-perlmutter-runbook.md)) |

The plugin also has `radexRead` (C++ reads fields from radex into the
running solver), but no example uses it. Showing the Python-to-C++
direction is stretch item S1, not part of the core demo.

## 3. Demo video (about 6 minutes, two parts)

**Part 1: OpenFOAM on RHAPSODY and Dragon, radex between C++ and Python
(about 3 minutes)**

1. Show the plugin interface: the `pitzDaily` case definition (Python) and
   the `radexWrite` entry in the case's `controlDict` (C++ side).
2. Start the optimization on a Perlmutter node.
3. Show a batch of solvers running concurrently, each writing its result
   into radex; the Python side reading the results from the store; the
   optimizer proposing the next batch; the loss falling.

**Part 2: the same workflow as an ORBIT service (about 3 minutes)**

1. From a laptop with no HPC login, start a RHAPSODY endpoint on
   Perlmutter through ORBIT.
2. Run the same driver from the laptop: solvers run on Perlmutter, the radex
   store lives in the endpoint next to them, and a Python task on the
   endpoint reads the C++ results from radex and returns only the losses.
3. Start a second, independent optimization instance from another client
   (a different target value) on the same endpoint. Both run side by side.
4. Query progress and best parameters of each instance remotely; tear both
   down.
