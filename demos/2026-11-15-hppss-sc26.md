## 1. Story

A digital twin of a flow rig watches a stream of measurements. When the
measurements drift away from what the twin predicts, the twin recalibrates
its CFD model by Bayesian optimization: it runs an OpenFOAM ensemble on
Perlmutter through ORBIT, exchanges results in memory through radex, and
updates a Gaussian-process surrogate that answers what-if queries in
milliseconds. The client is a laptop with no HPC login and no public IP.

The case is artificial; the infrastructure is real. It is the same pattern
as the NSTX-U digital twin planned for December 2026 (stream shot data,
predict, fine-tune on out-of-distribution data), with OpenFOAM standing in
for the fusion codes.

## 2. Workload

The OpenFOAM `pitzDaily` case, as used by
`examples/pitzDaily-optimize` in
[CrayLabs/rhapsody-plugins-openfoam](https://github.com/CrayLabs/rhapsody-plugins-openfoam):

| Property | Value |
|---|---|
| Physics | 2D backward-facing step, steady incompressible RANS (`simpleFoam`), k-epsilon turbulence model |
| Size per case | Serial, one core; no domain decomposition in the example |
| Calibrated parameters | 4: initial `epsilon`, `Cmu`, `C1`, `C2` (`sigmaEps` derived) |
| Observable | `avgInlets`, a scalar written by the `radexWrite` function object into a radex store |
| Loss | `(avgInlets - target)^2`; converged if the solver stops before 2000 iterations |
| Optimizer | `skopt.Optimizer`, Gaussian-process base estimator, batched `ask(n_points=ensemble_size)` / `tell()` |
| Example defaults | ensemble size 5, at most 10 iterations |
| Runtime per case | Not yet measured on Perlmutter (work item W1) |

In the demo, the twin's measurement stream replaces the fixed target: the
target becomes the latest (noisy) measured `avgInlets`.

Caveat: one scalar observable cannot pin down four parameters uniquely; the
optimizer finds *a* parameter set that matches the measurement. That is
acceptable for the demo story. Adding probe values as further observables
(stretch item S2) makes the calibration well-posed.

## 3. Demo flow (live part, about 5 minutes)

1. Laptop client creates a twin on the ORBIT broker (`dt` plugin) and opens
   the DT dashboard.
2. A sensor emits noisy `avgInlets` measurements from a hidden reference
   parameter set into the twin over ORBIT pub/sub.
3. A comparator agent tracks the residual between measurement and the twin's
   current prediction. The residual is small.
4. Drift: the presenter changes the hidden reference parameters. The
   residual crosses its threshold.
5. The calibration investigator starts a campaign. Each iteration: `ask()`
   a batch of parameter sets, submit one `pitzDaily` solve per set to the
   RHAPSODY endpoint on Perlmutter, solvers write into radex, the twin reads
   the losses, `tell()`. The dashboard shows task arcs to Perlmutter and the
   loss falling.
6. The GP surrogate answers a few what-if queries (mean and uncertainty) in
   milliseconds, versus about a minute per CFD run.
7. The residual returns below threshold. The twin is torn down; the laptop
   shows an empty service.

## 5. Mapping to STELLAR-AI and Genesis

| Demo element | STELLAR-AI / Genesis counterpart |
|---|---|
| Twin hosted in the ORBIT `dt` plugin | Digital Twin as a Service (DTaaS) |
| Recalibration on drift | Fine-tuning on out-of-distribution data |
| GP surrogate with uncertainty | SmartSurrogates / ROSE as a Service |
| Measurement stream into the twin | NSTX-U shot-data streaming |
| OpenFOAM ensemble | M3D-C1, GX and XGC campaigns |
| radex in-memory data plane | AI runs where the simulation data lives |
| Laptop drives Perlmutter through ORBIT | AmSC service layer: no HPC login, no public IP |
| Time per recalibration | The 5-10 minute between-shot target |
